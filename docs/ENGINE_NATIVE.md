# 0.2.0 실험용 네이티브 엔진

## 구현과 실제 사용 경계

이 버전에는 x86 네이티브 명령 수집·주입 엔진이 있습니다. 완성된 자동 관전 리플레이 제품은 아닙니다. **게임이 만든 동일한 초기 경기 상태에서만 재생을 시작하는 실험용 싱글플레이 어댑터**입니다. 경기 설정 자동 복원, 완전한 상태 스냅샷, 멀티플레이, 외부 PC 재생, 관전자 HUD/배속은 아직 지원하지 않습니다.

기록된 명령을 틱과 적용 순서대로 기존 게임 함수에 전달합니다. 시드와 호출 수, 게임 자체 체크섬을 재생 전·명령 전·명령 후 검사하고 차이가 나면 멈춥니다. 매 틱 난수 값을 강제로 덮어써 불일치를 숨기지 않습니다. 게임 자체의 32비트 체크섬은 상태 일부에 대한 진단값이며 모든 시뮬레이션 데이터의 동등성을 증명하지 않습니다. 테스트용 시뮬레이터 성공을 실제 KUF 경기 재현 성공으로 취급하지 않습니다.

## 테스트 방법

1. 기존 게임을 닫고 `dist/0.2.0/KUFReplayLauncher.exe` 실행.
2. `싱글플레이 경기 자동 기록` 체크 상태에서 게임 실행. 원본 실행 파일 SHA256을 검증하고 중지 상태로 게임을 생성합니다. 엔진 초기화 성공 후 게임을 진행합니다.
3. 싱글플레이에서 짧은 경기를 진행하고 정상적으로 경기에서 나옵니다. 게임 객체 종료 또는 경기 초기화 경계에서 기록을 마감합니다. 닫는 즉시 프로세스를 강제 종료하면 기록은 미완성으로 남을 수 있습니다.
4. 런처가 완료 기록을 검사·포장하고 목록에 표시하는지 확인합니다. 저장 폴더는 이전 버전과 같은 `%LOCALAPPDATA%\KUFReplay\Replays`입니다.
5. 게임을 닫고 목록에서 더블클릭. 실행된 게임에서 **기록 당시와 같은 지도·진영·슬롯·게임 규칙으로 싱글플레이를 시작**합니다. 지도·초기 상태가 일치하면 기록 명령을 처리합니다. 설정 자동 입력은 아직 구현하지 않았습니다.
6. 초기 상태 또는 진행 중 상태가 다르면 종료 여부 안내가 표시됩니다. `engine.log`에 상태 코드가 남습니다. 종료하지 않기로 하면 재생 시뮬레이션을 정지 상태로 유지합니다.

틱 속도는 실제 측정 전이라 초/분 시간 표시 대신 틱 수를 표시합니다. 지도 바이트는 리플레이에 포함하지만 현재 부트스트랩은 설치된 동일 지도 파일을 요구하고 기존 지도를 덮어쓰지 않습니다.

## 설치 파일과 실행 코드 보존

### Steam 실행 (런처 0.2.1)

하단의 `게임 실행 (Steam)`은 Steam App ID 2183600 프로토콜로 게임을 실행합니다. 네트워크 계정 안내창에서는 `아니요`를 선택합니다. 이 버튼은 엔진을 주입하지 않습니다. 아래 직접 EXE 실행 어댑터와 재생 경로는 여전히 실험용이며 Steam 부트스트랩 지원이 필요합니다. 기존 자동 기록 체크박스는 `실험용 기록 실행` 버튼으로 분리했습니다.

0.2.1 빌드의 하단 버튼으로 새 게임 프로세스가 시작되고 실제 첫 메뉴 화면에 진입하는 것을 확인했습니다. 해당 시험에서는 계정 안내창이 다시 나타나지 않았습니다. Steam 실행 요청·오류 처리 시험을 포함해 Python 테스트 총 23개가 통과했습니다.

`KUFReplayInjector.exe`는 정확히 `69f2575ad14c78d3c6f7c15d0187234be005f06abf095d3f1bd602f1c3722868` SHA256의 8,352,688-byte 실행 파일만 허용합니다. 이미 실행 중인 게임에는 붙이지 않습니다. 엔진 DLL은 런처 빌드에 포함된 파일만 로드하며 리플레이에서 DLL/EXE를 읽지 않습니다.

엔진은 ASLR 베이스를 기준으로 주소를 계산합니다. 원본 `.text`를 재배치 정보로 정규화한 후 실행 중인 코드 전체와 비교합니다. 각 후킹 위치의 명령 바이트/호출 대상도 별도로 검증합니다. 등록된 후킹 바이트를 반영한 기대 `.text`와 주기적으로 비교해 자체 후킹과 다른 코드 변조를 구분합니다. 자체 복원과 검사 사이에는 잠금을 사용합니다. 게임 설치 파일에는 쓰지 않습니다.

후킹 대상은 이 설치 빌드의 정적 분석에서 확인한 경계만 사용합니다:

- `KUFGAMEOBJ` 처리 함수 `0x4cf2b0`: 종료/상태 불일치 시 시뮬레이션 진행 정지.
- `0x4cfc55 → 0x4daf50`: 싱글플레이 명령 적용 틱 경계.
- `0x4db124`, `0x4db170 → 0x4db870`: 큐에서 적용되는 명령 바이트를 실제 적용 순서로 수집.
- `0x4d6d10`의 확인된 호출 지점: 경기 전환 시 이전 기록 마감.
- `KUFGAMEOBJ` 삭제 함수 `0x4c09f0`: 상태가 해제되기 전에 기록 마감.
- `0x4dae50`: 게임이 사용하는 자원/유닛 필드/난수 기반 32비트 체크섬.

일반 네트워크 큐와 명령을 파일로 읽는 기존 비활성 경로 `0x4db700`은 구조 확인에 참고했습니다. 비활성 기록 플래그를 켜 기존 동기식 디스크 쓰기 경로를 사용하지 않습니다.

## 기록과 외부 데이터

게임 스레드는 16MiB 용량의 버퍼에 크기 제한된 기록을 복사합니다. 별도 엔진 스레드가 `.partial`에 기록하고, 정상 종료 레코드가 있으면 flush → close → 완료 파일 이름 변경을 수행합니다. 최대 원시 기록은 128MiB입니다. 버퍼가 넘치면 게임을 기다리게 하지 않고 해당 기록을 무효화합니다. 실패·프로세스 강제 종료 기록은 정상 목록에 들어가지 않습니다.

런처는 원시 기록의 종류·크기·틱 순서·종료 여부를 검증한 뒤 기존 `.kufreplay` 보관함으로 옮깁니다. 기록 포장 실패는 원시 파일을 보존한 채 `.rejected`와 이유 JSON으로 격리합니다.

명령의 모든 객체 번호/생산 인자/지도 패킷 의미를 아직 검증하지 못했습니다. 따라서 재생은 이 PC에서 생성한 HMAC 인증 기록만 허용합니다. 외부 리플레이는 가져와 보관할 수 있지만 명령 주입은 거부합니다. 이 제한을 없애려면 명령별 의미 검증과 안전한 초기 상태 복원 구현이 먼저 필요합니다.

## 검증 결과

- C++ 어댑터의 실제 콜백을 ABI가 같은 테스트 모델로 구동: 두 명령 배치 기록/재생 결과 일치, 관전 입력 큐 폐기, 초기 난수 불일치 차단, 진행 중 상태 불일치 차단, 버퍼 초과 시 비차단 실패, 예상 바이트 확인·후킹·복원 통과.
- Python 컨테이너/컨트롤러: 모든 잘림 위치, 기록 순서, 명령 길이, 지도 경로 탈출, 완료 기록 포장·인증·재생 준비, 외부 PC/메타데이터 변조 거부, 실패 기록 격리 검증.
- 기존 보관함·업데이트 테스트 포함 총 21개 Python 테스트 통과.
- 런처 GUI 초기화 확인. 네이티브 DLL/주입기 x86 빌드 성공. 실제 설치 파일에 대한 해시 검사 및 이미 실행 중인 게임에 대한 중복 실행 거부 확인.
- 원본 게임의 초기화 안내가 닫힌 뒤 정상 경기 화면을 확인했습니다. 이미 시작된 경기는 후킹하지 않았으므로 실제 엔진 주입과 동일 경기 재현은 아직 확인하지 못했습니다. 기존 계정을 자동으로 변경하지 않았습니다.
